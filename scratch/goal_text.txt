- Confirm whether a module already exists before creating a new one.
- Do not invent table names.

- Do not invent file paths.
- Do not invent user roles.

If something is missing, document it first before creating it.

- Existing session logic unless broken.
- Existing user accounts.
- Existing students.
- Existing staff.
- Existing admissions.
- Existing results.

- Existing eLearning records.
- Existing links and navigation.
- Existing production workflows.

Only modify what is necessary.

## 3. Work in Small Verified Steps

For every phase:

1. Inspect relevant files and tables.
2. Identify current implementation.
3. Identify the problem.
4. Propose the smallest safe fix.
5. Implement only that fix.
6. Test affected pages.
7. Check for broken links.
8. Check for database errors.
9. Check permissions.
10. Document what changed.

Do not jump phases.

Do not make large unrelated changes.

---

## 4. Use Evidence-Based Implementation

Before editing any module, produce a short implementation note containing:

- Files found.
- Tables found.
- Current logic.
- Problem discovered.
- Safe improvement plan.
- Risk level.
- Backup recommendation.

Only then implement.

---

## 5. Protect Production Stability

Do not break working modules.

Before changing code:

- Back up the file.
- Avoid destructive database changes.
- Prefer additive migrations.
- Do not drop tables.
- Do not rename columns unless absolutely required.
- Do not remove working logic without replacing it safely.
- Preserve backward compatibility.
